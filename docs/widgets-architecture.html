하나의 선언적 spec으로
관통하는 위젯 시스템

supalens의 차별점은 Claude agent가 쿼리만 주는 게 아니라 어떤 차트로·어떻게 그릴지까지 결정한다는 것. 그래서 agent가 방출하는 시각화 spec을 축으로, 그 spec을 검증·렌더·영속화하는 3개 레이어를 쌓는다. 변환 레이어 없이 spec 객체 하나가 ask 답변 ↔ 저장된 위젯 ↔ 렌더러를 그대로 관통한다.

01

핵심 결론

agent는 propose_visualization 이라는 새 in-process MCP 툴로 차트 spec(JSON)을 방출하고 → spec은 단일 zod 계약(src/lib/viz/spec.ts)으로 검증되며 → registry 기반 <WidgetRenderer>가 spec.type을 보고 컴포넌트를 고른다.

데이터 구동 차트(bar·line·area·pie·scatter)는 Recharts 3, 단순 타일(KPI·bignumber·table)은 기존 dx-* CSS 그대로. 저장 시엔 같은 spec 객체를 dashboard_widgets.spec(jsonb)에 그대로 박고, 렌더 때 기존 executeReadOnly로 SQL을 재실행한다.

02

전체 데이터 흐름 — the seam

spec 객체가 agent → 스트림 → (즉시 렌더 │ 저장) → 재실행 → 렌더러를 단일 타입으로 관통한다.

Agent · Trigger.dev (locked-down, read-only)

① execute_sql  →  ② propose_visualization

execute_sql가 {columns, rows, queryId} 반환 → agent가 propose_visualization({queryId, chart}) 호출. 핸들러는 부모 프로세스의 in-memory Map만 읽어 zod 검증 + 컬럼 존재 검증 → DB·secret 안 건드림 (락다운 불변 유지).

VisualizationSpec { v, query, sample?, chart }
Stream

AnalysisChunk { type:'visualization', spec }

기존 Trigger Realtime / SSE가 한 줄 추가로 그대로 운반. agent_runs.result jsonb에 {text, sql, dataSourceId, spec} 저장 — ask 경로는 마이그레이션 불필요.

A · 즉시 렌더

/app/ask 답변

sample 행 스냅샷으로 그 자리에서 차트 표시. 추가 쿼리 없음.

B · 저장

"위젯 추가" 클릭

spec을 바이트 그대로 복사 → dashboard_widgets.spec + saved_queries.sql.

렌더 시 SQL 재실행
Read-only engine (재사용)

executeReadOnly(dataSourceId, sql)

SELECT-only · READ ONLY tx · supalens_ro 역할 · 감사 로그. 저장된 SQL이 물리적으로 read-only를 못 벗어남. → {columns, rows} 반환.

Render

<WidgetRenderer spec data /> → registry[spec.type]

단일 진입점이 spec을 zod로 다시 검증 → registry에서 컴포넌트 선택 → <Widget> 카드로 감쌈 (loading / empty / error / truncated 상태 포함).

spec

시각화 결정

소유: Agent (Layer 1)

어떤 차트 · 컬럼 매핑 · 포맷. 같은 쿼리를 오늘은 bar, 내일은 line으로.

query

데이터

소유: saved_queries

SQL + data_source. register_query MCP 툴과 1:1. 여러 위젯·알림이 재사용.

layout

배치

소유: dashboard_widgets

grid x/y/w/h. 유저가 정함. CSS Grid 렌더, 드래그 편집은 나중.

3개 관심사가 독립적으로 영속화되는 게 핵심 — 이래야 spec·query·layout을 따로 바꿀 수 있다.

03

단일 계약 — src/lib/viz/spec.ts

3개 에이전트가 위치를 두고 갈렸다(viz / widgets / dashboards). 하나로 통일: lib 레벨(React 없음)이라 agent·서버·클라이언트 전부 import. emit 전 / render 전 / write 전 — 전부 같은 스키마로 검증.

// 엔벨로프 — 서버 주입 필드(v/query/sample) vs 모델 작성 필드(chart) 분리
export const VisualizationSpec = z.object({
  v: z.literal(SPEC_VERSION),               // 버전 → 미래 migrateSpec() 업캐스트
  query: z.object({ sql: z.string(), queryId: z.string().optional() }),
  sample: Sample.optional(),                  // 즉시 렌더용 행 스냅샷(≤200, 저장 시 drop)
  chart: ChartSpec,                         // ↓ 렌더러가 switch하는 대상
})

// ChartSpec = 디스크리미네이티드 유니온 (dim1 ChartConfig = dim2 WidgetSpec, 하나로 통일)
export const ChartSpec = z.discriminatedUnion('type', [
  Kpi, BigNumber, Bar, StackedBar, GroupedBar, Line,
  MultiLine, Area, Pie, Donut, Scatter, Table,
])

// 데이터는 execute_sql 반환 그대로 — 어댑터 0
type WidgetData = { columns: string[]; rows: Record<string,unknown>[]; truncated?: boolean }

04

3개 레이어

Layer 1

Agent 통합

  • propose_visualization 툴을 buildSqlTools 안에 추가. ALLOWED_TOOLS+canUseTool 화이트리스트 등록
  • 락다운 불변 유지 — 핸들러는 in-memory Map만 읽음. pool·vault·KMS 무접근
  • 자가수정 루프 — 컬럼 불일치/zod 실패 시 유효 컬럼 목록을 에러로 반환 → 모델이 같은 턴에 수정
  • 폴백 — spec 없이 끝나면 마지막 쿼리로 table 자동 생성
  • system-prompt 규칙 — 데이터 모양 → 차트 타입 매핑
Layer 2

컴포넌트 라이브러리

  • Recharts 3 — React 19 정식 지원, SVG라 fill="var(--clay)"로 CSS 변수 직접 읽음, ResponsiveContainer
  • 단순 타일(KPI·bignumber·table)은 순수 dx-* CSS, 라이브러리 0
  • <WidgetRenderer> 단일 진입점 → registry → <Widget>
  • 차트는 next/dynamic({ssr:false}) + 스켈레톤 → KPI만 있는 페이지는 번들 안 받음
  • theme.ts — clay 램프 + 축/그리드 CSS var. 애니 ~400ms + reduced-motion
Layer 3

데이터 · 영속화

  • RSC 초기 렌더 + server action 갱신. route handler 안 씀 (creds server-only)
  • 인가 — admin client 호출 전 user-JWT로 RLS 선검증
  • 캐시 — unstable_cache(revalidate, tags) + revalidateTag. 기본 300s = "5분 전 갱신"
  • 3 테이블 — dashboards · saved_queries · dashboard_widgets (agent_runs RLS 규약 복제)
  • 그리드 — CSS Grid. react-grid-layout은 드래그 편집용으로 나중
